# Plan 页面：景点从哪里来，时间如何排出来

## 当前旅游示例

固定安排改为 **15:00–15:30 在 Palmer House 办理酒店入住**。这是输入中的示例安排，
不代表系统已经订了酒店。默认希望去的地点为 `Art Museum`。

在 Chicago 示例模式，`Art Museum` 是一个明确的小范围别名，映射到 Art Institute of Chicago。
这不是任意自然语言理解。四个候选地点、营业时间和价格来自 `services/demo.py` 中的预置列表，
没有调用 Overpass，也没有访问场馆官网。具体访问时间由排程器计算，不是整份日程硬编码。

默认输入会得到以下示例；修改固定安排后会重新找空档：

| 时间 | 活动 | 来源 |
| --- | --- | --- |
| 10:00–11:00 | 参观 Art Institute 艺术馆 | 示例候选地点 |
| 11:30–12:30 | 参观 Field Museum 展览 | 示例候选地点 |
| 13:00–14:00 | 逛 Millennium Park | 示例候选地点 |
| 15:00–15:30 | 酒店入住 | 输入中的固定安排，不能移动 |
| 16:00–17:00 | 沿 Chicago Riverwalk 散步 | 示例候选地点 |

交通仍为合成的 20 分钟估计，费用和营业时间也都是示例。景点卡片明确标为
`Sample hours · bundled`，每个活动写明来源。示例有效只表示相对于这些输入事实没有发现违规。

## 七步究竟是什么

| 页面步骤 | 实际操作 |
| --- | --- |
| Read your trip details | 读取城市、日期、时区、想去地点、预算和固定安排 |
| Load Chicago example places | 读取预置的四个 Chicago 示例地点；这一步没有联网 |
| Keep the original commitments | 单独保存酒店入住等固定安排，作为后续验证基准 |
| Load example travel estimates | 读取合成的 20 分钟交通数据；真实模式改为查询 OSRM |
| Prepare opening-hour checks | 将 `Mo-Fr 09:00-17:00` 等原文转换成具体日期的开放区间，尚不是最终校验，也不访问官网 |
| Arrange candidate activities | 在固定安排周围寻找能放入的访问时间 |
| Check the schedule | 独立检查重叠、交通间隔、营业窗口、预算和固定安排是否改变 |

此前三个步骤标为 `Example`，其余四个标为 `Done`，容易被误解成只有四个完成。
现在示例步骤显示 **Done · sample data**，正常示例会显示 **7/7 finished**。
操作完成不等于事实已经被官网验证。失败步骤另外标出 failed，不能当作成功数据。

## “规则排程”做了什么

它每次尝试一个 60 分钟访问，从最早日期开始，在 09:00–18:00 中每隔 15 分钟寻找开始时间。
如果与固定安排重叠、已知营业时间不覆盖整次访问，或相邻交通时间不足，就换下一个时间段。
找到第一个能放入的空档就安排进去；安排不下的地点列为未安排。最后仍交给独立验证器检查。

所以当前还没有全局最优路线、按天均衡、可变参观时长或自动按预算替换景点。
缺交通时排程暂留 30 分钟缓冲，但验证器仍报告交通未核实；缺营业时间也保留警告。

## 真实模式中的 Art Museum 和附近景点

1. Open-Meteo 定位城市及其当地时区。
2. 对用户明确输入的地点，通过 Nominatim 查询一次。`Art Museum` 是泛称，当前取第一条地图匹配；
   返回的是匹配结果的真实名称，而不只是重复输入文字。用户应核对是否为想去的场馆。
3. 有指定地点时，以第一个匹配地点为中心查附近景点；否则以城市定位点为中心。
   Overpass 查询最多 3 公里内的博物馆、景点和画廊，这不是热门程度排行榜。
4. 汇总地点的坐标、原始营业时间标签、网站标签，并查询 OSRM 驾车估计。
5. 用相同规则安排活动、验证结果。页面说明每个活动属于“用户指定地点”还是“附近地图结果”。

地图中的网站标签只是链接，当前没有抓取该网站或独立确认票价、营业时间和酒店库存。

## Overpass 失败时

- 错误信息保留 HTTP 状态或连接/超时原因，不再只给笼统的不可用提示。
- 只有明确的 HTTP 502/503/504 服务器错误，才在同一域名缩小到 1.5 公里重试一次。
- HTTP 403、429、代理拒绝或连接错误不触发替代域名请求或反复重试。
- 已经解析出指定场馆时，可以继续规划该场馆，并明确提示附近搜索失败、没有补造其他活动。
- 若只有城市且附近搜索失败，仍须报告无法获取候选地点，并建议输入具体场馆名称。

这些处理通过了注入响应测试；当前 Codex 网络仍限制独立访问 Render/地图服务，
不能据此声称用户所遇到的远端 Overpass 问题已经在真实网络中解决。需要部署新版后查看具体原因。

## 切换城市

Chicago、`芝加哥`、`Chicago, IL` 识别为同一个示例城市。输入其他城市后，表单会明显切换到
真实地图模式；提交时只移除未编辑过的 Chicago 酒店样例，用户自己添加或编辑过的固定安排保留。
后端 API 若明确收到 `data_mode=demo` 与其他城市，仍返回清楚的输入错误，避免把 Chicago 数据
冒充其他城市。页面不再等到规划最后才提示这个限制。

本次更新需要在 Render **Manual Deploy → Deploy latest commit** 后才会出现在公网页面。
